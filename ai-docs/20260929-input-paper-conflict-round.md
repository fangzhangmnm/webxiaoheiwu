## 1. 同步安全（v2.1.15，已推 dev）

**为什么要紧**：这是「字会不会丢」的问题，排在所有界面工作之前。

**核实结论**：库层面，冲突两种选法都先留底，书和 txt 走同一条路。

| 冲突面上选了什么 | 输掉的那一版去哪 |
|---|---|
| 云端覆盖本地 | **本机**备份箱（IndexedDB 的 backup 分区，只在这台设备上） |
| 本地覆盖云端 | **云端** `.backup/` 夹（OneDrive 应用文件夹里） |

注意第一行：输家**不在**云端的 backup 夹里，换设备就看不到。备份箱没有上限、没有自动清理。

**但 app 层有三条丢字路径**，用新搭的两台设备端到端测试抓到并修掉：

1. txt 稿选「云端覆盖本地」后，保存链自己等自己，之后打的字永远不落盘。
2. 书和 txt 选「云端覆盖本地」后，排着队的本地落盘把旧版本写回原名，下一次推送静默盖掉另一台设备的版本。
3. 干净快进下载途中正文没上锁，途中打的字被整篇覆盖且不进备份。

修法与规矩写在仓库 `CLAUDE.md`「世界线守卫」一条和 `src/rescue.ts` 文件头。

**测试台**：`npm run e2e:sync`（`test/e2e-sync/`）。真 app、真 store 库、真 IndexedDB，两个浏览器上下文当两台设备，云是库自带的内存假云。八个场景，约 75 秒。

**没做、要 user 定的**：

- **备份箱没有界面**。库有 `files.listBackup`，app 没接。冲突面小字写着「不会丢失」，但用户自己取不回来。
- **库里有一个洞**（不在 app 能修的范围，改库要先问 user）：库的「编辑游标」从没人标记过，所以库在「判一次脏」和「覆盖本地」之间没有二次校验。app 这边已经用 `localDirty` 回调和冻结输入绕开了它能影响的路径。
- 还原出厂设置会连本机备份箱一起清掉，说明文案没提。

## 2. 输入深模块与软键盘（v2.1.16，已推 dev）

**为什么要紧**：iPad 和手机是写作设备，光标乱跑等于没法写。

做了什么、规矩是什么，写在仓库 `CLAUDE.md`「输入深模块」一条（那里是 SSoT，这里不重复）。

**光标乱跑的排查结论**：

| 嫌疑 | 结论 |
|---|---|
| 点候选后候选条消失，手指抬起时落到底下的正文 | **头号嫌疑**。旧候选条上半截正下方就是正文（探针确认）。无头 Chromium 复现不了 iOS 的原生文字手势，所以按结构修，真机未验。 |
| 插入的钩子与 undo | 没发现会挪光标的路径。落字统一走 `replaceRange`，落完光标放在新字之后。 |
| 没收成窄接口 | 属实。输入接线以前散在 app.ts 里逐元素挂，章节名框组字时按回车会同时「上屏」和「提交改名」。已收进 `src/input/`。 |
| 嵌入态每次输入把正文框高度先设成 0 再量 | 会引起版面抖动，不改光标位置。第三批换成不碰正文框的量法。 |

**手机首选词出屏**：已复现并修掉。原因是拼音串排在候选前面，长拼音时独占 337 像素。

**要 user 真机看的**：键盘手感（键高、间距、抬手才算数的延迟感）；iPad 接实体键盘时软键盘让位是否顺；Quest 射线点键的大小。

## 3. 稿纸与小横屏（v2.1.17，已推 dev）

**为什么要紧**：GPD Win Mini 是写作主力设备之一，屏幕又矮又宽；稿纸线歪是每天都看得见的毛病。

**Win Mini 的物理现实**（2026-09-29 查证）：7 寸 1920×1080 原生横屏触摸屏，翻盖，拇指实体键盘，触摸板不可按压，机身 168×109 mm。

| 用法（按系统缩放 175% 算） | 网页可用区 |
|---|---|
| 全屏 | 1097 × 617 |
| 装成 app 的窗口 | 约 1097 × 537 |
| 浏览器标签页 | 约 1097 × 480 |

⚠ 这里把「175% 的 zoom」理解成 Windows 的显示缩放。如果 user 指的是浏览器里再放大 175%，可用区会小到约 731 × 411，宽稿纸档同样会生效，但一屏只有六七行。

**写字线先量后改**：`node tools/ruled-audit.mjs` 逐行量「字的墨迹底边到线」的距离。

| 量到的毛病 | 原因 | 修法 |
|---|---|---|
| 「标准 · 宽行」下线切字脚 | 线的位置写死成上挪 0.4 个字高，只对 1.9 倍行距成立 | 线位 = 实测基线 + 0.18 字高 |
| 越往下越歪 | 行高是小数像素，背景一块块平铺、逐块取整 | 行高取整数像素；线改成一张重复渐变 |
| 目录的字比正文的字低 1 像素 | 正文容器上沿落在零点几像素上 | 上沿补到整像素 |

**子节目录坐在线上**：每一行和正文同字号同行高，没有边框和底色，正文与目录之间空一行。

**宽稿纸**：可用区又矮又宽时自动每行 34 字、行距 1.7、上限 760 像素。设置里「稿纸宽度（本机）」可改成只跟阅读节奏或总是加宽。

| 设备与状态 | 改之前 | 改之后 |
|---|---|---|
| Win Mini 窗口态 | 约 9 行 × 22 字 | 13 行 × 34 字 |
| iPad mini 横屏 + 软键盘 | 7 行 × 22 字 | 9 行 × 34 字 |
| 手机横屏 + 软键盘 | 一行半 | 3 行 |

**要 user 看的**：34 字和 1.7 倍行距是 AI 定的起步值，手感归 user。iPad 竖屏和 VR 不受影响（仍是窄稿纸）。

## 6. 要不要加日文输入法（评估，未动代码）

**查到的事实**：

- RIME 有现成的日文罗马字方案 `rime-jaroomaji`（微软输入法风格）。方案文件 Apache-2.0；四本词典各自沿用上游许可证（mozc、JMdict、KANJIDIC2、mozc emoji），用了就要在产品界面里署名。
- 我们内置的引擎只带了中文方案的预编译表（全拼、双拼、五笔、笔画）。日文的表得自己用 librime 的部署工具编出来再放进仓库，体积没查到。
- 引擎本身（my_rime）是 AGPLv3+。这是既有事实，不是这次新增的。

**三个做法**：

| | 做什么 | 代价 |
|---|---|---|
| 不加 | 维持现状 | 无 |
| 只加假名 | 罗马字 → 平假名 / 片假名，不转汉字。表很小，可以自己写，没有词典许可证问题 | 小；软键盘要多一个语言档 |
| 完整日文 | 接 `rime-jaroomaji`，能转汉字 | 中到大：编表、体积、四份署名、候选行为要重新验 |

**建议**：如果只是偶尔要打人名、片假名外来语，做「只加假名」；要写成段的日文再上完整方案。要不要做、做哪一档归 user。
