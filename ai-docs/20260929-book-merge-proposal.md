# 提案：书的冲突改成「按页合并」

> created 2026-09-29 by Claude Fable 5.1 · as-of v2.1.18 / 2026-09-29 · **状态：提案，未拍板，未动代码**
>
> 起因：user 2026-09-29「加了书模式之后更改冲突模型变了。对于画来说只有一个 ssot，但是书更类似 git，里面有好多并行的工程。如果我设备 1 改了第一章设备 2 改了第二章怎么办。这个需要非常仔细的想。」
>
> 本文只摆事实、方案和要 user 拍板的问题。文中凡是「建议」都是 AI 的建议，不是决定。

## 1. 一句话

现在两台设备各改了同一本书的不同章节，冲突面只能二选一，输掉的那台设备改的章节整章离开这本书（进备份箱）。建议改成：**先收下云端那一本，再把本机改过的页放回去**；只有同一页两边都改了，才两个版本都留着让人挑。不需要改同步库。

## 2. 现状（2026-09-29 用两台设备端到端测试核实过）

一本书在云端是**一个文件**（`书名.webxiaoheiwu.zip`）。同步库按整个文件比对版本。

| 情形 | 现在发生什么 |
|---|---|
| 设备 1 改第一章并上传；设备 2 手里是旧版，改了第二章再上传 | 设备 2 弹冲突面：本地覆盖云端 / 云端覆盖本地 / 取消 |
| 设备 2 选「云端覆盖本地」 | 设备 2 的第二章改动整本进**本机**备份箱；书里只剩设备 1 的第一章改动 |
| 设备 2 选「本地覆盖云端」 | 设备 1 的第一章改动整本进**云端** `.backup/` 夹；书里只剩设备 2 的第二章改动 |
| 任何一种选法 | 字节不丢，但**没有界面能取回**；要手工从备份里把那一章抄回来 |

对画来说这是对的：一幅画只有一个真相，两台设备画了不同的东西，本来就只能留一幅。对书来说，两台设备改的是**不同的页**，二选一丢掉的东西远多于必要。

## 3. 问题陈述

- **输入**：本机这一本 M（有没上传的改动）、云端那一本 T（别的设备上传的）、两者共同的出发点 B（上一次本机与云端一致时的版本）。
- **输出**：一本合并后的书 R。
- **必须满足**（按数据安全词典序）：
  1. 云端任何一页的字都不被静默覆盖。
  2. 本机任何一页的字都不被静默丢掉。
  3. 两边改的是不同的页时，不需要人做任何选择。
  4. 同一页两边都改了时，两个版本都留在书里，人自己合。

难点在 B：同步库不保留出发点那一版的字节，本机保存一次它就被覆盖了。没有 B 就分不清「这一页和云端不一样」是我改的还是对方改的。

## 4. 三条路

| | 甲：维持二选一，补备份箱界面 | 乙：按页合并（建议） | 丙：一页一个云端文件 |
|---|---|---|---|
| 做法 | 冲突面不变；加一个界面列出备份、能取回 | 冲突时先收下云端，再把本机改过的页放回去 | 书在云端不再是一个 zip，而是一个文件夹，每页一个文件 |
| 设备 1 改第一章、设备 2 改第二章 | 仍然二选一，输家手工抄回 | 自动合并，两章都在 | 根本不冲突 |
| 同一页两边都改 | 二选一 | 两个版本都留在书里 | 这一页二选一 |
| 改同步库 | 不改 | 不改 | 大改（列举、改名、加密、封面都按文件夹重做） |
| 改书的格式 | 不改 | 加一个字段（见 5.2） | 推翻「书 = 一个 zip」（ADR-0008） |
| 工作量 | 小 | 中 | 很大 |
| 风险 | 低 | 合并逻辑写错会把页放错位置；有兜底（见 5.6） | 半同步状态（一半页是新的一半是旧的）、原子性没了 |

丙是粒度最自然的解，但它推翻 2.0 的根基决定，而且「一本书是一个完整的快照」这件事对备份、加密、分享都有价值。不建议。

甲的备份箱界面无论选哪条路都该做：冲突面上写着「被替换的版本会自动留底，不会丢失」，现在用户自己取不回来。

## 5. 乙的细节

### 5.1 核心想法

冲突时不再问「留哪一边」，而是做两步：

1. **收下云端那一本**（同步库现成的「云端覆盖本地」，本机那一版照旧先进备份箱）。
2. **把本机改过的页放回去**，存成一次普通的本地修改，再上传。

这相当于 git 的「先拉再把自己的改动接上去」。两步用的都是同步库已有的动作，所以库不用改。今天 v2.1.15 加的「世界线守卫」正好是接入点：现在它在第 1 步之后整体重载，合并就是在重载之前多做第 2 步。

### 5.2 怎么知道「本机改过哪些页」

在书的清单 `graph.json` 里加一个字段 `sync`，由本机在编辑时顺手记：

```json
"sync": {
  "touched": { "第二章.txt": 1727600000000, "新的一页.txt": null },
  "removed": { "废稿.txt": 1727500000000 },
  "renamed": { "旧名.txt": "新名.txt" },
  "tree": [ "…出发点那一版的主干树，只有本机动过树才记…" ],
  "links": { "第一章.txt": [ "…出发点那一版这页的链接，只有本机动过才记…" ] },
  "readOnly": false,
  "cover": true
}
```

- `touched`：本机改过或新建的页。值 = 这页在出发点那一版的修改时间戳；新建的页记 `null`。
- `removed`：本机删掉的页，值同上。
- 其余几项只在本机动过对应的东西时才出现。

**什么时候清空**：本机与云端重新一致的那一刻（上传成功、拉到新版、收下云端）。清空只在内存里做，下一次保存自然写出去，不为清空单独重写文件。

**别的设备写的记号怎么办**：一律不信。打开一本书时，同步库说它是干净的（没有未上传的改动），就把读到的 `sync` 丢掉；只有本机确实有未上传改动时才沿用。

**时间戳只做相等比较**，不比大小。「云端这页的时间戳等于出发点的时间戳」= 对方没碰过这页。不同设备的时钟谁快谁慢不影响结论。这一点守住了家规「无 LWW」：从不用「谁的时间更新」来决定留谁。

### 5.3 合并规则

R 从云端那一本 T 起步，然后逐条处理本机的记号：

| 本机做了什么 | 云端那边 | 结果 |
|---|---|---|
| 改了页 P | 没碰 P | R 里的 P = 本机版本 |
| 改了页 P | 也改了 P，内容不同 | **两版都留**：P 保持云端版本；本机版本另存为紧挨着的一页「P（本机 月日-时分）」 |
| 改了页 P | 也改了 P，内容恰好一样 | 什么都不用做 |
| 改了页 P | 删了 P | 留下本机版本（改过的字不因为对方删页而消失），提示一句 |
| 新建页 Q | 没有同名页 | 加进 R |
| 新建页 Q | 也新建了同名页，内容不同 | 两版都留，本机那页改名加后缀 |
| 删了页 P | 没碰 P | R 里删掉 P，指向它的链接一并清掉 |
| 删了页 P | 改了 P | 留下云端版本（对方改过的字不因为我删页而消失），提示一句 |
| 把 P 改名为 Q | 没碰 P | R 里 P 改名为 Q，云端各页指向 P 的链接改指 Q |
| 把 P 改名为 Q | 改了 P | 两页都在：P = 云端版本，Q = 本机版本 |
| 没碰的页 | 任何改动 | 全部照云端 |

原则只有一条：**有字被改过的那一方永远留下**。删除和改名输给修改。

### 5.4 主干树和链接

页的内容好合并，结构要小心。

- **本机没动过树**：树照云端。这是最常见的情形（只是在写字）。
- **本机动过树，云端没动**：树照本机。
- **两边都动过树**：逐页决定它的父亲和位置。一页的父亲只有一方改了就照改了的那方；两方都改了照云端，并提示。合并完检查不变量（一个名字在树里至多一次、不成环）；不满足的页退回云端的位置，云端树里没有的页接到书的末尾。**页不会因为树合并而消失**，最坏情况是顺序要人再理一下。
- **链接**：同理，逐页三方比较；两边都改了就取并集，保留云端的顺序，本机新加的接在后面。
- **修改锁、封面**：只有一方改了照改了的那方；都改了照本机。
- **上次读到哪一页、回退栈**：这是设备自己的导航状态，照本机。

### 5.5 界面

冲突面（只对书；txt 稿维持现状）：

```
「樱川中学科学部」在你编辑期间被别的设备改过。

[ 合并两边（推荐）]   [ 云端覆盖本地 ]   [ 本地覆盖云端 ]   [ 取消 ]

被替换的版本会自动留底，不会丢失。
```

合并完给一句结果，不弹第二个框：

- 「已合并：本机改的 2 页已并入。」
- 「已合并。『第三章』两边都改过，两个版本都留着，多出来的一页叫『第三章（本机 0929-1432）』。」

### 5.6 出错时的兜底

合并是一段纯函数，输入两本书和记号，输出一本书和一份报告。它写错了会怎样：

- 合并函数抛错，或者结果没通过不变量检查 → **退回今天的行为**：云端那一本照常载入，本机那一本整本另存为「书名 冲突留底」（v2.1.15 已有）。
- 合并结果上传时云端又变了 → 再来一轮（收下新的云端，把刚才合并出的改动再放回去）。
- 无论如何，第 1 步之前本机那一版已经在备份箱里。

也就是说，合并最坏的结果等于今天最好的结果。

## 6. 要 user 拍板的事

1. **走哪条路**：甲 / 乙 / 丙。
2. **书的格式加字段**：`graph.json` 加 `sync`。家规要求 zip 内容的任何增改都要给 user 完整清单：新增的只有这一个键，没有新文件。旧版本的 app 读到它会忽略、保存时会把它丢掉（读 `format.ts` 确认：解包只取认识的键，打包只写认识的键）；后果是那台旧版本设备上的冲突退回二选一，不会坏书。
3. **同一页两边都改了，原名留给谁**：建议原名留给云端版本，本机版本另起一页。理由：云端那一版别的设备还在用，它的名字不动，几台设备反复合并时不会来回倒。反过来也不丢字，只是手感不同。
4. **合并要不要问**：建议保留冲突面、把「合并」放成第一个按钮。另一种做法是不弹框直接合并，事后只给一句提示。家规「冲突必 surface」倾向前者。
5. **打不打算做文字级的合并**（同一页里两边改了不同的段落，自动拼起来）：建议不做。v1 时 user 定过「不要 diff」；两版并排留着让人自己合，出错面小。
6. **备份箱界面**：建议做，放在书库的回收站旁边。只列出、取回、清空三个动作。

## 7. 不做的事

- 不做文字级合并、不画冲突标记。
- 不做改名侦测（靠内容相似度猜「这页是那页改了名」）。改名由本机如实记在 `renamed` 里，对方的改名无从得知就按「删了旧的、加了新的」处理，结果是两页都在。
- 不比较不同设备的时间先后。
- 不改同步库的持久化结构。
- txt 稿不在本提案范围内（它没有页）。

## 9. 提案接口（.h）

现状接口见 `api/project/session.d.ts`、`api/project/mode.d.ts`。提案新增一个模块，其余模块只多几个调用点。

```ts
// src/project/merge.ts（新）——纯函数，无 DOM、无 store
export interface SyncMarks {
  touched: Record<string, number | null>;   // 页名 → 出发点的修改时间戳；null = 本机新建
  removed: Record<string, number>;
  renamed: Record<string, string>;          // 旧名 → 新名
  tree?: TreeNode[];                        // 出发点的主干树（本机动过树才有）
  links?: Record<string, string[]>;         // 出发点的链接（本机动过的页才有）
  readOnly?: boolean;                       // 出发点的修改锁（本机动过才有）
  cover?: true;                             // 本机换过封面
}
export type MergeNote =
  | { kind: "kept-both"; page: string; mineAs: string }
  | { kind: "edit-beat-delete"; page: string; keptSide: "mine" | "theirs" }
  | { kind: "tree-conflict"; page: string }
  | { kind: "appended-to-end"; page: string };
export interface MergeResult { project: Project; notes: MergeNote[]; appliedPages: number }
/** 把本机的改动放到云端那一本上。抛错 = 调用方退回整本留底。 */
export function mergeOntoTheirs(mine: Project, marks: SyncMarks, theirs: Project, opts: { now: number; suffix: (page: string) => string }): MergeResult;
/** 合并结果相对云端那一本的记号（合并后本机的新出发点 = 云端那一本）。 */
export function marksAgainst(result: Project, theirs: Project): SyncMarks;

// src/project/session.ts（改）
//   每个改动动词顺手记 SyncMarks；open 时由调用方告知「这一本有没有未上传的改动」决定沿用还是丢弃读到的记号；
//   新增 adoptedFromCloud() / pushed()：清空记号。

// src/project/format.ts（改）
//   ProjectGraphJson 多一个可选键 sync?: SyncMarks；pack / unpack 原样读写。

// src/store-ui.ts（改）
//   resolveConflict 对书多一个按钮「合并两边」；选了它 → 对同步库回答 takeCloud，并记下「这一本收下云端之后要合并」。

// src/project/mode.ts（改）
//   worldWasReplaced()：有「要合并」的记号 → 读云端那一本、mergeOntoTheirs、存成本地修改、上传；否则维持现在的整体重载。
```

同步库这边**可选**的一个小请求（不是前提）：文件句柄上多一个 `isDirty()`，省得 app 从文件夹列举里查。要不要提交给库，归 user 定。

## 10. 如果选乙，分三期

| 期 | 内容 | 交付物 |
|---|---|---|
| 一 | 备份箱界面；`sync` 记号的读写与清空；合并纯函数与单测 | 能看到备份；记号在记，但还不拿来合并 |
| 二 | 冲突面加「合并两边」；接进世界线守卫；端到端场景 | 两台设备改不同章节能自动合并 |
| 三 | 真机打回后的调整；ADR 落档 | ADR |

每一期结束都可以停。第一期做完即使不继续，备份箱界面也是独立有用的。
