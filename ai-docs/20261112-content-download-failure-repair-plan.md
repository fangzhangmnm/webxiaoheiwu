# 施工单：云端文件内容下载不下来时，小黑屋的六处毛病

> created 2026-11-12 by Claude Fable 5.2（小黑屋维修线统筹）
> as-of 小黑屋 v3.0.20 / 同步库 2.3.2 / 2026-11-12
> 施工 = 小黑屋维修线小弟（user 开的会话）。统筹只写这张单、定规矩、审第 1 和第 3 条。

## 一、出了什么事

2026-11-12 下午，user 在办公室的一台 Windows 机器上（Edge，开发版 v3.0.20）打不开云端。黑匣子里看到的：

- 登录正常，每次开页面 1 秒内自动续上。
- 向微软问「有哪些文件、各是哪一版」正常（中间有一次微软回 504）。
- 把文件内容下载下来这一步连着失败十几次，每次都是 `downloadUrl: network fetch failed (TypeError: Failed to fetch)`。下载走的是微软另一台发文件的服务器，和登录、列文件不是同一个地址。
- 云端的日记本比这台机器新，必须下载才能跟上。下不来 → 进门的检查 8 秒没结果 → 显示连不上 → user 点离线继续 → 弹出「云端有新版本，保留哪一边」。

根源是办公室网络拦了那台服务器，还是微软当天不稳，**黑匣子里的信息分不清**。这不归我们修。归我们修的是下面六处。

## 二、已经读代码确认的事（施工时不用再查）

- 「本地覆盖云端」= 同步库 `src/works/safe-resolve.ts` 的 `weakOverride` → `cloud.weakOverride`：先在云端把被换掉的那份拷进 `.backup`，再带 If-Match 覆盖。**不需要下载**，所以下载不通时按它，字节不丢。
- 「云端覆盖本地」= `safePull`：先把本机那份无条件备份，再 `cloud.pull`。下载不通时 pull 抛错，本机字节不动（多了一份备份）。
- 下载失败的报错在同步库 `src/base/providers/graph.ts` 的 `downloadItemBlob`（约 240 行），只有一句话，没有文件名、主机、用时。
- 小黑屋 `src/app-store.ts` 建云端连接时没传 `transport`；MoonSinger、CatsUp 都传了 `{ timeouts: DEFAULT_GRAPH_TIMEOUTS, chunkResume: true, verifyChunkedCommit: true }`。
- 冲突的框在小黑屋 `src/store-ui.ts` 的 `resolveConflict`（约 52 行）。

| 1 | 下载失败的报错带上：阶段、主机名、文件名、用了多少毫秒 | 同步库 | 统筹 | 没开始 |

### 第 1 条：报错要能分清是谁的问题

同步库出补丁版 2.3.3。

- `CloudNetworkError` 加两个可选字段：`stage`（`"graph"` 或 `"content"`）和 `host`（只有主机名）。`downloadItemBlob` 和按范围下载的那几处抛的填 `"content"`；经 `graphFetch` 抛的填 `"graph"`。
- 报错的字里带上：主机名、文件名（拿得到就带）、从发出到失败用了多少毫秒。例：`downloadUrl: network fetch failed host=xxx.example file="a.txt" after=1234ms (TypeError: Failed to fetch)`。
- **硬规矩：下载地址是带签名的临时地址，拿到它就能下载文件。整条地址、查询串、路径都不许进报错、不许进黑匣子。只许主机名。** 这条配一个测试守着：报错的字里不许出现 `?`、`tempauth`、`sig=` 这类片段（测试里用一条带假签名的地址去撞）。
- `downloadUrl failed <状态码>` 那一支也带上主机名和用时。
- 黑匣子里 15:59:11 有一行光秃秃的 `timeout`，没有上下文。找到它是哪里打的，补上是哪个请求、等了多久。

为什么这么做：今天就是因为缺这几样，分不清是网络拦的（通常几十毫秒就失败）还是那边没回音（通常十几秒）。以后别的 app 碰到同类问题，也靠这几个字段。

### 第 2 条：提示说实情

- 小黑屋 `store-ui.ts` 的 `reportError`：`CloudNetworkError` 且 `stage === "content"` 时，换一句话。中文定稿：「云端连得上，但文件内容下载不下来。可能是这个网络拦了微软发文件的服务器，或者微软那边暂时有问题。本地已保留，稍后自动重试。」英文照意思写，走 i18n。
- 进门的闸在这种情况下的说法也用同一句的意思，不要说成没网。
- 没有 `stage` 字段（老的报错）照旧走原来那句。

### 第 3 条：「保留哪一边」的框说实话

规矩（统筹定的，施工不改；觉得不对停下来问）：

- 同步库记一个事实：**这个页面里，最近一次下载文件内容是失败的，而且之后还没有成功过**。只记这一件，不猜原因、不设时限。下载成功一次就清掉。
- 同步库叫 `ui.resolveConflict` 时，在参数里多给一个可选字段 `contentFailing: boolean`，就是上面那个事实。
- 小黑屋的框，`contentFailing` 为真时：
  - 多一行字。中文定稿：「云端那份的内容现在下载不下来。选「云端覆盖本地」现在完不成；选「本地覆盖云端」会把别的设备写的换成这台的，被换掉的那份进备份箱。」
  - 默认钮（高亮的那个）从「云端覆盖本地」换成「取消」。
  - **三个钮都留着，一个都不藏、不变灰。** user 的规矩是不硬拦，只说清楚。
- `contentFailing` 为假或没给：框和现在一模一样。
- 库的那条顺序（先备份再覆盖）一个字都不动。这一条只加一个事实、一个参数字段，不加第二条化解的路。

测试：
- 库：下载失败后叫冲突的框，参数里 `contentFailing` 是真；之后成功下载一次再叫，是假。
- 小黑屋：`contentFailing` 为真时，框里有那行字、默认钮是取消、三个钮都在；为假时和现在的快照一样。

### 第 4 条：开请求超时

`src/app-store.ts` 照 MoonSinger 的写法传 `transport`。三个开关一起开（另外两个是分块上传断了能接着传、分块传完核对一遍），和两个兄弟同形。开完跑红线那一组。大的书上传要是因为超时变得传不上去，停下来报，不要自己调数字。

### 第 5 条：只查不改

出事那天，黑匣子里这台机器最后一次上传日记本是 11-11 中午，当天下午核过是同步的；11-12 出事前没有本机写字的记录。可是框里说「在你编辑期间被别的设备改过」，另一个画面里还有一个开头是「还有 1 份…」的框。

要回答的：在下载一直失败、进门检查超时、user 点了离线继续的情况下，有没有哪条路会在 user 没写字时把这份稿标成有改动（比如开稿时重新存了一遍、加密的稿重新封了一遍）。读代码回答，能写成测试复现最好。查到了**不要顺手修**，写进页末的施工记录，报给统筹。

### 第 6 条：两个框叠在一起

user 截图里，「正在检查云端…（跳过，先离线打开）」压在另一个等 user 回答的框上面，后面那个框的字和钮都看不到。

规矩：一个等 user 回答的框亮着时，别的框不许盖在它上面。先查清是哪两个框、什么顺序出来的，再定是排队还是让转圈框让位。不许用「自动把后面那个关掉」来解决，那等于替 user 回答了。

## 四、通用的规矩

- 版本号：同步库 2.3.2 → 2.3.3，小黑屋 v3.0.20 → v3.0.21，都只升补丁号。同步库不建 GitHub 发布页（权限拦着，等 user）。
- 同步库只有小黑屋收这一版。MoonSinger、CatsUp 的仓库和会话不碰；它们以后自己收。
- 同步库仓库和小黑屋仓库里，只提交自己改的文件，不用 `git add -A`。
- 做的顺序：第 1、3 条的库改动 → 出包 → 小黑屋收库 → 第 2、3、4、6 条 → 第 5 条。库改完、小黑屋收之前，先在页末记一笔并告诉统筹来审第 1、3 条的库那一半。
- 推：红线那一组在要发的提交上是绿的，就推开发版，别的测试推完再跑。正式版不推。
- 浏览器测试一律无头。测试不出声。
- 流程图文档（小黑屋 ai-docs 里的 pipelines，如果有）和 `api/` 跟着同一个提交更新。
- 提交要署名（模型和日期）。
- 碰到这张单没写的设计决定：停下来，写在施工记录里，问统筹。
