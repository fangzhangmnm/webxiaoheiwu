# 施工单：云端文件内容下载不下来时，小黑屋的六处毛病

> created 2026-11-12 by Claude Fable 5.2（小黑屋维修线统筹）
> as-of 小黑屋 v3.0.20 / 同步库 2.3.2 / 2026-11-12
> 施工 = 小黑屋维修线小弟（user 开的会话）。统筹只写这张单、定规矩、审第 1 和第 3 条。

## 一、出了什么事

2026-11-12 下午，user 在办公室的一台 Windows 机器上（Edge，开发版 v3.0.20）打不开云端。黑匣子里看到的：

- 登录正常，每次开页面 1 秒内自动续上。
- 向微软问「有哪些文件、各是哪一版」正常（中间有一次微软回 504）。
- 把文件内容下载下来这一步连着失败十几次，每次都是 `downloadUrl: network fetch failed (TypeError: Failed to fetch)`。下载走的是微软另一台发文件的服务器，和登录、列文件不是同一个地址。
- 云端的日记本比这台机器新，必须下载才能跟上。下不来 → 进门的检查 8 秒没结果 → 显示连不上 → user 点离线继续 → 弹出「云端有新版本，保留哪一边」。

根源是办公室网络拦了那台服务器，还是微软当天不稳，**黑匣子里的信息分不清**。这不归我们修。归我们修的是下面六处。

## 二、已经读代码确认的事（施工时不用再查）

- 「本地覆盖云端」= 同步库 `src/works/safe-resolve.ts` 的 `weakOverride` → `cloud.weakOverride`：先在云端把被换掉的那份拷进 `.backup`，再带 If-Match 覆盖。**不需要下载**，所以下载不通时按它，字节不丢。
- 「云端覆盖本地」= `safePull`：先把本机那份无条件备份，再 `cloud.pull`。下载不通时 pull 抛错，本机字节不动（多了一份备份）。
- 下载失败的报错在同步库 `src/base/providers/graph.ts` 的 `downloadItemBlob`（约 240 行），只有一句话，没有文件名、主机、用时。
- 小黑屋 `src/app-store.ts` 建云端连接时没传 `transport`；MoonSinger、CatsUp 都传了 `{ timeouts: DEFAULT_GRAPH_TIMEOUTS, chunkResume: true, verifyChunkedCommit: true }`。
- 冲突的框在小黑屋 `src/store-ui.ts` 的 `resolveConflict`（约 52 行）。

### 第 1 条：报错要能分清是谁的问题

同步库出补丁版 2.3.3。

- `CloudNetworkError` 加两个可选字段：`stage`（`"graph"` 或 `"content"`）和 `host`（只有主机名）。`downloadItemBlob` 和按范围下载的那几处抛的填 `"content"`；经 `graphFetch` 抛的填 `"graph"`。
- 报错的字里带上：主机名、文件名（拿得到就带）、从发出到失败用了多少毫秒。例：`downloadUrl: network fetch failed host=xxx.example file="a.txt" after=1234ms (TypeError: Failed to fetch)`。
- **硬规矩：下载地址是带签名的临时地址，拿到它就能下载文件。整条地址、查询串、路径都不许进报错、不许进黑匣子。只许主机名。** 这条配一个测试守着：报错的字里不许出现 `?`、`tempauth`、`sig=` 这类片段（测试里用一条带假签名的地址去撞）。
- `downloadUrl failed <状态码>` 那一支也带上主机名和用时。
- 黑匣子里 15:59:11 有一行光秃秃的 `timeout`，没有上下文。找到它是哪里打的，补上是哪个请求、等了多久。

为什么这么做：今天就是因为缺这几样，分不清是网络拦的（通常几十毫秒就失败）还是那边没回音（通常十几秒）。以后别的 app 碰到同类问题，也靠这几个字段。

### 第 2 条：提示说实情

- 小黑屋 `store-ui.ts` 的 `reportError`：`CloudNetworkError` 且 `stage === "content"` 时，换一句话。中文定稿：「云端连得上，但文件内容刚才没下载下来。本地已保留。」（11-12 统筹审稿改：库记的是「最近一次失败、之后没成功过」，不一定是此刻，不说死成现在；重审裁定五：猜原因的半句删掉，只说事实）英文照意思写，走 i18n。
- 进门的闸在这种情况下的说法也用同一句的意思，不要说成没网。
- 没有 `stage` 字段（老的报错）照旧走原来那句。

### 第 3 条：「保留哪一边」的框说实话

规矩（统筹定的，施工不改；觉得不对停下来问）：

- 同步库记一个事实：**这个页面里，最近一次下载文件内容是失败的，而且之后还没有成功过**。只记这一件，不猜原因、不设时限。下载成功一次就清掉。
- 同步库叫 `ui.resolveConflict` 时，在参数里多给一个可选字段 `contentFailing: boolean`，就是上面那个事实。
- 小黑屋的框，`contentFailing` 为真时：
  - 多一行字。中文定稿：「这台设备刚才有文件内容没能从云端下载下来。选「云端覆盖本地」可能完不成；选「本地覆盖云端」会把别的设备写的换成这台的，被换掉的那份进备份箱。」（11-12 统筹审稿改，理由同第 2 条；重审裁定五：库记的是全页面的事实、不一定是这一篇，不指「那份」。开文件那张面只有两个钮，只放到「可能完不成。」）
  - 默认钮（高亮的那个）从「云端覆盖本地」换成「取消」。
  - **三个钮都留着，一个都不藏、不变灰。** user 的规矩是不硬拦，只说清楚。
- `contentFailing` 为假或没给：框和现在一模一样。
- 库的那条顺序（先备份再覆盖）一个字都不动。这一条只加一个事实、一个参数字段，不加第二条化解的路。

测试：
- 库：下载失败后叫冲突的框，参数里 `contentFailing` 是真；之后成功下载一次再叫，是假。
- 小黑屋：`contentFailing` 为真时，框里有那行字、默认钮是取消、三个钮都在；为假时和现在的快照一样。

### 第 4 条：开请求超时

`src/app-store.ts` 照 MoonSinger 的写法传 `transport`。三个开关一起开（另外两个是分块上传断了能接着传、分块传完核对一遍），和两个兄弟同形。开完跑红线那一组。大的书上传要是因为超时变得传不上去，停下来报，不要自己调数字。

### 第 5 条：只查不改

出事那天，黑匣子里这台机器最后一次上传日记本是 11-11 中午，当天下午核过是同步的；11-12 出事前没有本机写字的记录。可是框里说「在你编辑期间被别的设备改过」，另一个画面里还有一个开头是「还有 1 份…」的框。

要回答的：在下载一直失败、进门检查超时、user 点了离线继续的情况下，有没有哪条路会在 user 没写字时把这份稿标成有改动（比如开稿时重新存了一遍、加密的稿重新封了一遍）。读代码回答，能写成测试复现最好。查到了**不要顺手修**，写进页末的施工记录，报给统筹。

### 第 6 条：两个框叠在一起

user 截图里，「正在检查云端…（跳过，先离线打开）」压在另一个等 user 回答的框上面，后面那个框的字和钮都看不到。

规矩：一个等 user 回答的框亮着时，别的框不许盖在它上面。先查清是哪两个框、什么顺序出来的，再定是排队还是让转圈框让位。不许用「自动把后面那个关掉」来解决，那等于替 user 回答了。

### 6.2 推翻或改正的（统筹之前说错的）

1. 「今天的下载是很快就失败」：错。每次等了 9–15 秒才失败。
2. 「选云端覆盖本地、下载失败时会自动再试一次、不行就停在只读」：错，那是另一条路。实际是：本机那份先留一个底，然后下载失败、报错、什么都不换，本机照旧能写、照旧算没传。每按一次多一份留底。
3. 「本地覆盖云端不用下载，可能传得上去」：前半句对，后半句是猜的。留底那一步要去问一个不在微软主接口上的地址，今天可能也不通。不通就停在覆盖之前，什么都不动。
4. 「过滤签名地址的做法我认可」：错。14 种写法漏 9 种。改法见第五节之后统筹发的裁定一（2.3.5：上游报错原文一个字不抄）。真实浏览器的下载报错本身不带地址，所以线上没有漏过；问题是定了「一个字不出」的规矩、却放行了一个挡不住的做法和一条让人放心的测试。
5. 第 4 条（开请求超时）：撤。固定的墙上钟时限会把慢网上「慢但传得完」变成「永远传不完」。这条是统筹一开始的错误猜测带进来的，和事故无关。
6. 「按取消最稳」：不成立，见 6.3 第 2 条。

### 6.3 重审查出的问题（按要紧程度）

1. **冲突框被盖掉 = 那一篇之后的保存全部落不了盘。** 锁屏位只有一个，五种脸共用，后叫的直接重画，先叫的 promise 永远没有结果。库在等人回答时占着那个文件的写队，后面的保存（含只存本机的）全排在它后面。实验：磁盘停在弹框前那一版。早就埋着，不是这次改出来的。小黑屋里日常的几条路碰巧被别处的判断挡住了，没挡住的组合：改名问旧文件的框和冲突框互相盖、开文件的转圈框盖冲突框。**这轮修小黑屋这一头**（裁定四）。库那一头另记，见 6.4。
2. **取消不是「先不管」。** 按了取消，15 秒后再推、再撞、再试着下载比对（下载不通时白等十几秒）、再弹同一个整屏的框，一直循环。能让它停下来的只有「本地覆盖云端」。整个系统在把人往那个钮上推。家规 10-26 已有「隐式动作撞上不模态」。**等 user 定。**
3. **闸门明知云端更新却放人在旧的那份上写。** 稿是干净的、云端有新版、下载失败 → 库回「快进失败」→ 闸门当成没事放行 → 人写字 → 必然撞冲突。出事那天后半段就是这条。MASTER §A 的 ready-gate 那一行说的是「核对完再放行输入」。**等 user 定。**
4. **「云端通不通」被当成一个开关。** 进门的检查、离线后的自动重连都只问一句元数据。今天是元数据通、内容不通，于是选了离线继续之后一分钟内被自动拉回在线、接着弹框。有了第 2、3 条的改法之后这条不再伤人，先记着。
5. **下载回来的字节没有和可信的那一路对账。** 文件大小来自微软主接口，内容来自另一台服务器，库不比对。小黑屋对没加密的文本稿只拦「像网页」的内容。内容那一路要是回了一段别的文字，会被当成新版本收下，本机干净副本不留底，之后一改一推就把云端真的那份盖掉。概率低；书和加密稿拦得住。另记，见 6.4。
6. **报错还是分不清是谁的问题。** 主机名加用时不够：浏览器把「服务器回了一个不许跨站读的错误」和「根本连不上」报成同一句话。要分清得另发一个探测。另记。
7. **黑匣子是给人导出去发给别人的，但它没有写下来的「什么不许进」。** 现在进了的：文件名、请求路径、微软的请求号。这轮只加出口那一层过滤（裁定二）。

### 6.4 记成结构问题、这轮不做的（归谁、什么时候动）

| 事 | 归谁 | 什么时候必须动 |
|---|---|---|
| 库在等人回答时不该占着那个文件的写队 | 同步库设计，统筹出稿、user 批 | 下一次动同步库的冲突或保存之前；或任何一家再报「打的字没存上」 |
| 整份传输的超时改成「多久没进展」，小黑屋才开超时 | 同步库设计 | 再有一次请求挂死的真案；或 MoonSinger / CatsUp 报慢网传不上去 |
| 下载回来的字节和主接口给的大小（或哈希）对账 | 同步库设计 | 下一次动下载这条路之前 |
| 普通对话框和锁屏位两套弹框系统没有统一管「谁在等人」 | 小黑屋界面 | 再出现一次两个框叠着 |
| 假云盘没有「元数据通、内容不通 / 挂着不回 / 很慢」这类故障的正式开关 | 同步库测试件 | 下一次给同步库加测试件时 |
| 报错分清「连不上」和「连上了但读不了」的探测 | 同步库，要 user 同意多发这一个请求 | user 说做 |
| 别家（MoonSinger / CatsUp / WeebPaint / KudsRocket）的锁屏位、黑匣子出口有没有同样的毛病 | 各家碰到时 | 各家下一次动同步界面时对一遍 |

### 6.5 事故原因，现在的判断

- **排除了的**：小黑屋的离线壳（只接管本站请求）；外发白名单（黑匣子里没有一行拦截记录）；新同步库把下载弄坏（下载这条路的代码在 2.2.5 和 2.3.2 之间一个字没变）。
- **更像微软那边**：出事头一分钟有一次向微软主接口问元数据，等了大约 30 秒，微软自己回了网关超时。办公室网络拦截造不出这种回应。下载失败的 9–15 秒也和「那边超时后回了一个读不了的错误」对得上。
- **不能排除办公室网络**：9–15 秒同样对得上域名解析超时。网上没查到当天的公开故障报告。
- **这台机器上，新同步库从来没有成功下载过一次**（11-11 起只核对过版本相同）。这不是证据，是提醒：不能拿「之前好好的」当理由。
